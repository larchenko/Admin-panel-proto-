Modals

Instrument record

#instrument · .dialog.dialog-lg, 768px · Spartan: hlm-dialog

The one modal the Admin panel has so far, and every state it can be in. Creating an instrument and reading one are the same dialog in two modes (decision 91): there is no second entry point and no view-then-edit step, so the fields are live from the moment it opens.

Nothing below is a copy. The frame is the real Instruments screen, loaded with ?state= telling it which state to open — a documentation hook in instruments.js that product code never reads. So this page cannot drift from the thing it documents: if the modal changes, what is drawn here changes with it.

Modes

One dialog, one data-mode attribute. Every part that belongs to only one mode carries data-only and is hidden rather than rebuilt, so the two modes cannot drift apart and the body keeps its markup (decision 75).

StateHow it is reachedWhat is different
The New instrument button in the page header. No status badge, no switch, no Products card, no tabs, no Delete. Footer is Cancel · Create instrument. The title is fixed text, not a field's echo.
A row's name, or its View details icon. Header gains the name, the status badge, the switch that changes it and the Products card; two tabs appear. Footer is Delete instrument at the left end, then Close · Save changes. Save is disabled.
One keystroke or one changed select, anywhere in the form. Only Save changes enables. app.js sets data-dirty on the form[data-guard]; the same flag is what the discard question reads. The header title follows the Name field as it is typed.
The second tab, Instrument performance. The price chart, its six-period toggle group (decision 94) and Refresh data. Drawn, and does nothing in the prototype. The footer does not change with the tab.
Opening an instrument whose row is inactive. The badge reads Inactive and the switch is off. Everything else stays readable and editable — deactivating stops the market-data updates, it does not lock the record.

Before it closes

A confirmation that opens over an open dialog is a popover="manual" inside it, never a second <dialog>: one Escape closes a whole stack of native dialogs, which would answer the question by discarding the work it is asking about (decision 68).

StateHow it is reachedWhat it asks
Close, Escape, or a click on the backdrop — but only while the form is dirty. A clean form closes without a question. Cancel · Discard changes. The guard is generic (app.js, #confirm-discard), so any dialog with a form[data-guard] gets it without writing anything.

Before it acts

Two acts work on the whole record rather than on a field — deactivating and deleting — and both ask first, through the one element #confirm-record. One element, because the two questions have the same shape: what it does, how many products feel it, one answer (decision 100).

StateHow it is reachedWhat it asks
The header switch, off only. Switching on applies at once — it restores what deactivating stopped and loses nothing. Cancel · Deactivate. The switch is put straight back until the answer comes, so it never shows a state the record does not have.
Delete instrument in the footer, while one or more products read the instrument. Not a question — a refusal. The title says it cannot be deleted, a warning names the count, and the single button is Back to the instrument. An instrument with products on it is almost always wrong rather than unwanted (95).
Delete instrument with a product count of zero. Cancel · Delete instrument (destructive). No undo and no message afterwards — the row leaving the list is the message.

The same question, asked from the list

A row's Delete icon can delete without opening the record, so the question exists a second time — #confirm-delete, a real modal <dialog> this time, because nothing is open underneath it for an Escape to take down with it. Same two answers, one difference: the refusal here can offer the record, which the record's own copy cannot.

StateHow it is reachedWhat it asks
Row menu → Delete instrument, with products on it. Cancel · Edit instrument. The second button opens the record, which is what was almost always wanted.
Row menu → Delete instrument, with no products on it. Cancel · Delete instrument (destructive). Identical wording to the record's, and deliberately so: one act, one sentence, wherever it is asked from.

Rules

  • One modal per record. Reading and editing are the same screen, so there is no Edit button to press and no state where the fields are shown but dead.
  • The primary action never opens a confirmation in red. Delete instrument in the footer is btn-outline; the destructive fill belongs to the answer, not to the question.
  • A confirmation over an open dialog is a manual popover, not a dialog (68). A confirmation with nothing open under it is a dialog.
  • Every confirmation names the record it is about. Delete Apple Inc.?, never Delete this item? — the modal is reused for every row, and the name is the only thing telling the admin which one they are answering for.
  • The status switch sits outside the form. It has its own confirmation, it never makes Save changes light up, and closing the record never asks to discard it.

Not drawn yet

Stated so that the gaps are not mistaken for decisions.

  • No field is ever invalid. The record has no validation state — nothing sets aria-invalid, so the error the Form field recipe draws has never been seen on this modal. Required fields, and what Create instrument does when one is empty, are open.
  • Nothing is ever pending. .skeleton exists in the recipes and the record does not use it: every value is in the markup, so there is no state for a value still being fetched — which the record view will have as soon as it reads a real source.
  • Saving is instant and silent. Save changes closes the dialog; there is no saving state on the button, no failure, and no confirmation that it worked. The loading state is drawn in the kit and unused here.
  • Two of the states above are forced. No instrument in the demo data has a product count of zero, so the destructive branch of both delete confirmations cannot be reached by clicking. ?state=delete and ?state=list-delete set the count to zero on the way in. The branch is real; the data has no case for it.
