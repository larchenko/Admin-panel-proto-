Table

Spartan: hlm-table · shadcn: table.tsx

The list view of every entity. Toolbar above (search, filters, primary action), the table itself, footer below (count, pagination). The toolbar in this demo keeps its filters inline, which works up to about four; past that they move into the Filters panel and the toolbar keeps only the search box and the button (89). No wrapper border and no radius: on a screen whose whole job is one list, a card frame draws a box around the only thing on the page. What structures it instead is the header band — tinted, closed by a rule above and below, and set in the overline role (12/600, secondary grey) so it differs from the data by size, weight and colour and not by its tint alone — a rule under every row, and the row hover. A sortable header is a button that fills its cell, so its hover band is the whole column, edge to edge, and lines up with the row band under it. A row that is out of use carries data-inactive (the last row below): its values drop to the secondary grey and its colour accents lose weight, while the status badge keeps full strength — it is the one thing that explains why the row is quiet. Every row is padded 3 (12px) left and right — the same unit the columns are spaced with — so the band under a hovered row is wider than its text on both sides; the wrapper bleeds the same 12px outwards, which puts the first column back on the page edge, in line with the search field above it and the count below it. Rows are 40px high; a checked row stays highlighted. Data below is illustrative.

Rules

  • First text column is the entity name, medium weight, and is the link to the detail view.
  • Identifiers in font-mono, numbers right-aligned with num, secondary columns in muted.
  • Status is always a badge, always in its own column, never coloured text.
  • Row actions live in the last column behind one More button. Max one inline action besides it.
  • Sortable headers are buttons; aria-sort tells the icon which way to point.
  • The last row keeps its rule — flat on the page there is no card edge to close the table.
  • The table never carries a frame of its own. If one is needed — a table inside a card or a dialog — the frame belongs to the container, and the table's cells sit flush against that container's padding.
  • A row that is out of use carries data-inactive: values in the secondary grey, colour accents at 60%, badge at full strength.
  • Empty, loading and error states of the table are separate components (next).

Column chooser

A list view outgrows the screen long before it runs out of useful fields. One popover answers both halves of that problem — which columns are shown and in what order — and both are a per-user setting, not a layout constant. It opens from an icon at the top of the row-actions column, directly above the row action icons: the toolbar answers "which rows", the table header answers "which columns". That column is not pinned, so on a table wider than the screen the control scrolls away with it — the pinned column is the first one, the row's identity (see below). Live on the Instruments screen; recipe in components.css under Column chooser, behaviour in app.js.

What may be turned off
Everything except the entity name, which is the row's identity and the link to the detail page. The row-actions column is not in the menu at all. Anything else — status included — is the user's business.
What may be offered at all
A field earns a column only if it is short enough to scan in one line, present on most rows, and worth comparing down the column. A UUID, a prose error, a field that only one instrument type has: detail page.
One value per cell
A cell never carries a second line. A value that qualifies another — the source of a price, the industry group of a sector, the identifier of a name — is a column of its own, in the menu like any other; a date and its time are one value, 18 Sep 2026, 10:12:03. One value per cell is what lets a cell be edited in place as one control (decision 108).
Order
The list is the order, top to bottom. Drag the handle, or focus it and use ↑ / ↓ — the keyboard path is not optional. Hidden columns keep their place, so switching one back on returns it where the user left it.
Lift, and the list opens a gap
Grabbing the handle lifts a floating copy of the row that follows the pointer. The row's own slot becomes an empty gap, and the rows in between slide one row over to carry that gap to where the drop will land — so what you read is the shape the list is about to take, not a marker describing it. The order changes on release, never under the pointer: the gap is drawn with transforms and the DOM is left alone until you let go, so the rows you are aiming at never move out from under you.
Reset
One action, restoring the default set and the default order. There is no per-row "restore".
Pinned column
Opt in with data-pin-first on the .table-wrap: the first column goes sticky left-0, because on a wide table the one thing that must never scroll away is which row you are looking at. Only one column is pinned — two would squeeze the data between them. A pinned cell paints its own background, so every row state (default, hover, selected) is repeated on it by hand as an exact colour mix; add a row state and you add it there too. The inner-edge shadow is state, not decoration: it appears only once the table is scrolled.
Persistence
Per user, like the collapsed sidebar rail. A shared default that one user's change moves for everybody is the thing this component exists to avoid.

For the developer

The header row is the map. Only <th> carries data-col; body cells carry nothing and are reordered by the same permutation. Columns not listed in the menu are pinned where they are — a leading checkbox column stays left, actions stays right.

Spartan · the popover is hlm-menu with checkbox items; in Angular the column set is state, so bind [hidden] and the *ngFor order to it instead of moving DOM nodes as the prototype does.

Drag · pointer events, not HTML5 drag-and-drop: a native drag inside a popover in the top layer is unreliable and cannot be tested. Angular should use the CDK's cdkDropList, which is this same pattern out of the box — a drag preview, a placeholder, and neighbours that animate aside — plus the keyboard behaviour.

The floating copy lives in the popover · it is appended to the menu, not to body: the popover is in the top layer, and anything outside it paints underneath however high its z-index. Dragging to the list's edge scrolls it on a frame loop, because the pointer can sit still at the edge.

Where the row will land is read off the resting layout · measured once at the grab, in the list's own coordinates so it survives that scrolling. Reading it off where the rows are now lets a row that has slid aside change the answer, and the gap flickers between two places.

Empty state · the "no results" row's colspan has to follow the visible column count.
