Button

Spartan: hlmBtn · shadcn: button.tsx

Triggers an action. Base class btn plus one variant, optionally one size. Default size is 36px high.

Variants

Left to right: descending emphasis. One default per screen.

btn-default · the primary action of the screen or dialog: Save, Create

btn-secondary · a second action of equal weight next to a default

btn-outline · common secondary actions: Cancel, Export, Filter

btn-ghost · low-emphasis, toolbars, icon buttons in tables

btn-destructive · irreversible actions only, inside a confirmation

btn-link · inline in text, or "View all" style links

Sizes

Default 36px. Small 32px for dense table rows and toolbars. Large 40px is rare; use for empty-state calls to action.

With icons

Icon sits before the label. Icon-only buttons need aria-label and a tooltip.

States

Hover darkens the fill slightly. Focus shows a 3px ring (press Tab). Disabled fades to 50% and ignores the pointer. Loading swaps the icon for a spinner and disables the button.

Rest

Focus (Tab to it)

Disabled

Loading

Rules

  • One btn-default per view. If two actions compete, one of them is outline.
  • Destructive buttons never sit alone on a page; they live inside a confirmation dialog.
  • Labels are verbs: Save, Create instrument, Cancel. Not "OK", not "Yes".
  • In dialogs and forms the primary action is on the right, Cancel to its left.
  • Use <button type="button"> unless the button submits a form.

<button type="button" class="btn btn-outline btn-sm">Cancel</button>

Spartan equivalent: <button hlmBtn variant="outline" size="sm">Cancel</button>. Variant and size names are identical.

Form field

Spartan: hlm-form-field, hlmLabel, hlm-hint, hlm-error

The wrapper every control lives in. Label above, control, then an optional description or an error. Label and control are linked with for/id; description and error with aria-describedby.

Shown to end users in the product list.

ISIN must be 12 characters.

Rules

  • Fields are required by default. Mark the exceptions with label-optional. No asterisks.
  • Description explains format or consequence in one sentence. Do not repeat the label.
  • Error replaces the description, names the problem and, where possible, the fix.
  • Validate on blur and on submit, never on every keystroke.
  • Two fields side by side only when they are short and related (field-row): currency and amount, first and last name.
  • Three across (field-row-3, decision 85) only for values that are one thing in parts — SIX Code, SIX Schema and SIX Bc are one identifier, and over two rows they read as two unrelated pairs. It is not a way to fit more in; a row of three unrelated fields is three fields nobody reads as a group.

Select

Spartan: hlm-select · shadcn: select.tsx

Pick one from a short list (up to ~15 items). A trigger button that looks like an input, and a list that opens below it. Fully custom, so it is identical in every browser. Behaviour is in app.js: click or Space/Enter/arrows to open, arrows to move, Enter to choose, Escape to close. For long lists use a searchable combobox (later).

Where it opens (decision 80). Below the trigger, and above it when it does not fit below and there is more room above — so a select near the bottom of the screen opens upward and one near the top opens downward. The side is decided every time it opens, and again while it is open if the page scrolls or the window resizes. The list is then capped to the room that side has, so a long one scrolls inside itself instead of running off the edge; 288px stays the ceiling. Same 4px gap and 8px screen gutter as the row-action menu, which has always flipped this way.

data-prefer="top" on the list asks it to start upward — for a select that sits in a page footer, where the screen edge is the whole point, like Rows per page in the table footer. It is a preference, not a lock: with no room above it opens downward like everything else.

Why not a tick and a dash
Both are thin marks of about the same size, so a column of them reads as texture rather than as two states. A filled square against an empty square differs in shape, weight and colour at once — and still differs with the colour taken away.
Why not a real disabled checkbox
Disabled means "you could change this, but not now". Nothing here is ever editable in the list, and the 50% opacity would undo the contrast we just bought.
The one difference from the control
No shadow-xs. Same size, radius, border and fill; the missing lift is the cue that it does nothing.
For the developer
Not a Spartan component — plain markup. Do not reach for hlm-checkbox with [disabled] here.

Metrics

Ours — no shadcn or Spartan equivalent

A row of counts between a page title and the list below it: what the set is made of, and what in it needs someone. Four cells at most, all the same width. A cell is a div when it is only a number and a button when the number filters the list — both look the same at rest, and the cursor and the pressed state say which is which.

Total instruments 248
Active 231 17 inactive

Zero is a state, not an empty cell. The count stays where it was, the colour goes, and there is nothing left to filter to — so the cell stops being a button. A strip that changes shape when the news is good cannot be read at a glance.

Small, and on its own. One cell, in a dialog header, where it must not tie with the 24px title beside it: metric-sm takes the padding down a step and the value to 20px. An <a> rather than a button when the number leads somewhere else — it gets the same hover and focus ring as a clickable cell. The instrument record's Products count is the built example (decision 97).

Products 293

Rules

  • Four cells at most. Every one has to earn the 90px it takes off the top of the list; a fifth number that nobody acts on turns the row into decoration.
  • The last cell is the one that is wrong. Left to right the row goes from what the set is to what needs doing, so the eye lands on the alert last and stays there.
  • A count only becomes a button when clicking it lands on exactly that number. Where the screen shows one page of a longer set, only a count computed over the rows can promise that.
  • Destructive here is the status colour, not an accent: a 5% tint with text in the -ink shade, the same recipe as a soft badge. One loud cell in four, and it is loud for a reason.
  • The value is 24px, the h2 step of the type ladder, but it is a number and not a heading — no h2 in this row.

Alert

Spartan: hlm-alert · shadcn: alert.tsx

A message about the thing on screen, in the flow of the page. Not a toast (it does not disappear) and not a tooltip (it is not an expansion of something else). Used for the result of a data fetch and for a save that failed. Variants use the status tokens with the -ink text shade, so each one clears 4.5:1 on its own tint (decision 24).

Neutral, for something the user should notice

Rules

  • Title is one line and says what happened; the description carries the detail and the way out.
  • Destructive for something that failed, warning for something that is stale or risky, success only as the answer to an action the user just took. Never as decoration.
  • An alert that reports a failure never removes the action that caused it — the user has to be able to retry.

Dialog

Spartan: hlm-dialog · shadcn: dialog.tsx

A record, opened over the screen it belongs to. Built on the native <dialog> with showModal(), so the focus trap, the inert background, Escape and the top layer are the browser's (decision 8). Two sizes: 512px, and dialog-lg at 768px for a record with field groups. Height caps at 85vh and only the body scrolls — the title of the record and the buttons that act on it are never scrolled away.

The small one is the shape both of the record's confirmations take: what the act does, how many products feel it, one answer. Built on the Instruments screen as #confirm-record — Deactivate from the switch in the record header, Delete instrument from the button in its footer (decision 100) — and as #confirm-delete on the list itself (95).

Anatomy

<dialog class="dialog dialog-lg" id="instrument" aria-labelledby="t">
  <div class="dialog-header">   title + status (+ switch?) · a metric cell? · close   ← fixed
  <!-- footer may carry one destructive verb at its left end: .dialog-footer-start -->
  <div class="dialog-body">     .form-sections            ← scrolls
  <div class="dialog-footer">   secondary + primary       ← fixed
</dialog>

Rules

  • Field groups inside are .form-section — a heading and a rule. Never cards: a card in a dialog is a frame inside a frame and indents its content away from the dialog's edges.
  • Read-only values are .props text, never disabled inputs. Disabled says "editable, but not now" and drops to 50% opacity — the wrong message and the wrong contrast for data that is being read.
  • A form that can lose work carries data-guard: closing it while it is dirty asks first, whether the user clicked Cancel, the backdrop, the X, or pressed Escape.
  • The confirmation is a popover="manual" element inside the dialog. Two native constraints, both found by testing: one Escape closes every native dialog in the stack at once, and a modal dialog makes everything outside itself inert, so a popover that is not its descendant renders but cannot be clicked. In Spartan this is hlm-alert-dialog on a CDK overlay and neither applies.
  • One primary action, bottom right. The destructive answer in a confirmation is the primary-looking one only when destroying is what the user asked for.
  • A confirmation that the data can refuse has two answers in one component: the plain destructive question, and — when something depends on the record — the number that refuses it plus the action that was almost always wanted instead. The buttons of the case that does not apply are removed, never disabled. Instruments · Delete instrument is the built example (decision 95).

Filters

Spartan: hlm-popover · shadcn: popover.tsx

A list with more than about four filters does not put them in the toolbar: past that they eat the width the search box and the primary action need, and none of them is used often enough to earn a permanent slot. They go in one panel behind a Filters button, and the button carries the number of them that are on (decision 89). Because a shut panel hides the query, a chip row sits under the toolbar: one chip per filter the panel holds, each clearing itself, so the list is never narrowed by something invisible. A filter whose own control is on screen — the search box, a type tab, a summary cell that filters — gets no chip; two copies of one state is one too many. Nothing is applied by a button: every change filters at once, so the footer count moves while the panel is open. Clear all means all — the panel, the search box and any filter parked in a control elsewhere.

Fields are laid out two across, which is what keeps the panel short enough to open downward under the toolbar. A pair of fields that is one filter — pick a field, then Empty or Filled — is ruled off as its own group with an overline: the Instruments list asks that of all twelve identifiers that way instead of carrying twelve controls (decision 90). Until both halves are set the filter does nothing, and the second select stays disabled so that half a filter never looks like a whole one.

Table

Spartan: hlm-table · shadcn: table.tsx

The list view of every entity. Toolbar above (search, filters, primary action), the table itself, footer below (count, pagination). The toolbar in this demo keeps its filters inline, which works up to about four; past that they move into the Filters panel and the toolbar keeps only the search box and the button (89). No wrapper border and no radius: on a screen whose whole job is one list, a card frame draws a box around the only thing on the page. What structures it instead is the header band — tinted, closed by a rule above and below, and set in the overline role (12/600, secondary grey) so it differs from the data by size, weight and colour and not by its tint alone — a rule under every row, and the row hover. A sortable header is a button that fills its cell, so its hover band is the whole column, edge to edge, and lines up with the row band under it. A row that is out of use carries data-inactive (the last row below): its values drop to the secondary grey and its colour accents lose weight, while the status badge keeps full strength — it is the one thing that explains why the row is quiet. Every row is padded 3 (12px) left and right — the same unit the columns are spaced with — so the band under a hovered row is wider than its text on both sides; the wrapper bleeds the same 12px outwards, which puts the first column back on the page edge, in line with the search field above it and the count below it. Rows are 40px high; a checked row stays highlighted. Data below is illustrative.

Column chooser

A list view outgrows the screen long before it runs out of useful fields. One popover answers both halves of that problem — which columns are shown and in what order — and both are a per-user setting, not a layout constant. It opens from an icon at the top of the row-actions column, directly above the row More buttons: the toolbar answers "which rows", the table header answers "which columns". That column is not pinned, so on a table wider than the screen the control scrolls away with it — the pinned column is the first one, the row's identity (see below). Live on the Instruments screen; recipe in components.css under Column chooser, behaviour in app.js.

What may be turned off
Everything except the entity name, which is the row's identity and the link to the detail page. The row-actions column is not in the menu at all. Anything else — status included — is the user's business.
What may be offered at all
A field earns a column only if it is short enough to scan in one line, present on most rows, and worth comparing down the column. A UUID, a prose error, a field that only one instrument type has: detail page.
Second lines are not columns
A second line belongs to its column — the source under a price, the time under a date. It is shown and hidden with that column and never appears in the menu on its own.
Order
The list is the order, top to bottom. Drag the handle, or focus it and use ↑ / ↓ — the keyboard path is not optional. Hidden columns keep their place, so switching one back on returns it where the user left it.
Lift, and the list opens a gap
Grabbing the handle lifts a floating copy of the row that follows the pointer. The row's own slot becomes an empty gap, and the rows in between slide one row over to carry that gap to where the drop will land — so what you read is the shape the list is about to take, not a marker describing it. The order changes on release, never under the pointer: the gap is drawn with transforms and the DOM is left alone until you let go, so the rows you are aiming at never move out from under you.
Reset
One action, restoring the default set and the default order. There is no per-row "restore".
Pinned column
Opt in with data-pin-first on the .table-wrap: the first column goes sticky left-0, because on a wide table the one thing that must never scroll away is which row you are looking at. Only one column is pinned — two would squeeze the data between them. A pinned cell paints its own background, so every row state (default, hover, selected) is repeated on it by hand as an exact colour mix; add a row state and you add it there too. The inner-edge shadow is state, not decoration: it appears only once the table is scrolled.
Persistence
Per user, like the collapsed sidebar rail. A shared default that one user's change moves for everybody is the thing this component exists to avoid.

For the developer

The header row is the map. Only <th> carries data-col; body cells carry nothing and are reordered by the same permutation. Columns not listed in the menu are pinned where they are — a leading checkbox column stays left, actions stays right.

Spartan · the popover is hlm-menu with checkbox items; in Angular the column set is state, so bind [hidden] and the *ngFor order to it instead of moving DOM nodes as the prototype does.

Drag · pointer events, not HTML5 drag-and-drop: a native drag inside a popover in the top layer is unreliable and cannot be tested. Angular should use the CDK's cdkDropList, which is this same pattern out of the box — a drag preview, a placeholder, and neighbours that animate aside — plus the keyboard behaviour.

The floating copy lives in the popover · it is appended to the menu, not to body: the popover is in the top layer, and anything outside it paints underneath however high its z-index. Dragging to the list's edge scrolls it on a frame loop, because the pointer can sit still at the edge.

Where the row will land is read off the resting layout · measured once at the grab, in the list's own coordinates so it survives that scrolling. Reading it off where the rows are now lets a row that has slid aside change the answer, and the gap flickers between two places.

Empty state · the "no results" row's colspan has to follow the visible column count.
